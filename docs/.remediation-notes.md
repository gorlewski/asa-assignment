## Why we bumped dependencies during Task 4 (not Task 3)

- We deliberately fixed vulnerable dependencies *during containerisation* so the
  Dockerfile ships with **no fixable vulnerabilities we could reasonably remove**.
- Rationale: we would rather enter the security-analysis phase with a clean image
  than knowingly build and publish an image carrying fixable CRITICAL/HIGH CVEs.
- Priority was to **drive CRITICALs to zero** (and HIGH where feasible) at build
  time — even where a given CVE may not be directly exploitable in our runtime,
  because it *could* be genuinely risky and the cost of bumping was low.
- The nuanced "vulnerability vs. our actual runtime" analysis (is the CVE
  reachable given how *we* use the library?) is done in **Task 3**, where we
  separate: what was fixed, what is residual, and why.
- Result recorded at time of writing: Python layer CRITICAL 1 -> 0, HIGH 17 -> 10.
  Tests remained green (18 passed) after every bump.

## Supply-chain safety policy: 3-7 day rollout delay

- Policy: we do **not** adopt brand-new/just-released dependency versions on the
  day of release. We wait **3-7 days** before pulling a fresh release into the
  build.
- Rationale: recent software supply-chain attacks (e.g. the compromised `axios`
  ecosystem incidents, the `Shai-Hulud` npm worm, and similar) have shown that
  malicious or compromised releases are often caught by the community within days.
  A short quarantine window materially reduces the risk of ingesting a poisoned
  release.
- This is a deliberate, documented policy — not negligence or staleness. Pins are
  explicit and reviewed; upgrades are intentional and lagged.

## Shift-left scanning policy (document in BOTH summaries)

- We run **Trivy IaC (`trivy config`) against the Helm chart locally BEFORE
  committing and BEFORE merging the PR** — not only in CI. Same for the
  Dockerfile (`trivy config`) and the built image (`trivy image`) and SAST
  (`semgrep`) / secrets (`gitleaks`).
- Rationale: shift-left. We do not push IaC or images and rely on CI to catch
  problems after the fact; we validate locally first so what lands is already
  clean. CI then re-runs the same gates as a backstop.
- Evidence at time of writing: Helm chart -> trivy config 0 misconfigurations
  (97/98 checks pass, the one default-namespace LOW was fixed by namespacing);
  Dockerfile -> 0 misconfigurations; hadolint clean.
